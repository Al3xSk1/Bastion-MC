title: bastion-mc: a Minecraft launcher for Arch Linux that treats the game as hostile code description: bastion-mc is a pre-release, unofficial Minecraft launcher for Arch Linux. It runs the game in a stacked sandbox, by default keeps your access token out of it, and says plainly what it does not defend. ---

Pre-release · unofficial · Arch Linux · built from source

A Minecraft launcher for Arch Linux that treats the game as hostile code

bastion-mc runs the game in a stacked sandbox. By default the game reaches the network only through the launcher's allowlisting relay, and it holds a placeholder instead of your access token. It is for people who play on Arch Linux, assume that a mod, a server or a downloaded world may be malicious, and are prepared to build the launcher themselves and to sign in through an Azure application of their own.

Fabric instances also get the launcher's own companion mod, with an in-game phone: Spotify, Discord and other sites you list in a browser that runs in a sandbox of its own, clips, approvals of Realms joins and settings sync. The mod is interface only: the launcher decides what each command from the phone may do, and no secret of these services enters the game.

What it does, layer by layer

The game's Java process is treated as hostile from its first instruction. A malicious or compromised mod is arbitrary Java and native code inside that process, and a server or a piece of content that triggers a bug in the game ends up with the same capability.

Each block below says what is in force at one layer and names what stays open there. The blocks are a summary: the security overview goes through the mechanisms one by one, and the attack surface matrix of the threat model has every row, with the attack, the defence, what remains and, where there is one, the test or the experiment behind the claim.

01 · What may run

Verified downloads and signed mod profiles

What the game is started from is fixed before it starts: Mojang's files by the hashes Mojang publishes, mods by a manifest that you signed.

In force

  • Every Mojang file is checked against the published hash chain when it is downloaded and again at every launch. A mismatch aborts the launch, and nothing is fetched again unless you ask for it with --repair.
  • A modded instance exists only by virtue of a manifest you signed (Ed25519). At launch the signature, the manifest's serial, every loader library and every jar in mods/ are verified; one extra, missing or modified file aborts the launch.
  • An older signed manifest is not accepted again, and a manifest is bound to its instance.
  • Mods fetched from Modrinth with bastion-mc profile add are checked for size and SHA-512 before they reach mods/, and they count for nothing until you sign the manifest.
  • Java comes only from root-owned runtimes under /usr/lib/jvm; the launcher never downloads one.
  • The game is given only the resource and shader packs you recorded: bastion-mc pack import checks, hashes and records a pack, and bastion-mc pack adopt records packs you copied in by hand. The game can read packs but cannot put one on disk.
{{REQUIRE README.md "Mods fetched from Modrinth with profile add are checked for size and SHA-512 (and SHA-1, where the registry lists one) before they reach mods/, and they are nothing until you sign the manifest."}}

Stays open

  • Mojang publishes SHA-1 hashes only, so the check relies on SHA-1's second-preimage resistance.
  • A loader library that has no published hash is trusted on first use when you create the profile; your signature then freezes it.
  • A signature fixes which jars run, by name, size and SHA-256. It says nothing about what they do: a mod you signed can still be malicious, and a server or a piece of content can still trigger a bug that runs an attacker's code inside the game. The other layers are for those cases.
  • Modrinth's hash and file come from the same party: a compromised project account, or the registry, serves a bad jar with a matching hash. A build younger than 48 hours is passed over, which is a delay, not detection.
  • The one mod that runs without being in your manifest is the launcher's own companion mod, part of the launcher binary (block 07).
  • Other software running as you can add a signing key of its own unless root-owned keys exist in /etc/bastion-mc/trusted-keys.d/, and the file that remembers a manifest's serial is writable by you.
{{REQUIRE docs/THREAT_MODEL.md "The hash and the file come from the same party. A compromised project account, or the registry, serves a bad jar with a matching hash"}} {{REQUIRE docs/THREAT_MODEL.md "A delay, not detection"}} {{REQUIRE README.md "The one mod that runs without being in your manifest is the launcher's own companion mod"}}

02 · Where the game runs

The sandbox

bubblewrap namespaces, then Landlock, then a seccomp allowlist, inside a systemd scope with memory and task limits. With the default audio = "pulse", the deliberate holes are one audio socket, the GPU and one display socket; block 05 is about them. Setting audio = "none" removes the audio socket, and audio = "alsa" hands the game the raw sound devices instead. In a Fabric profile the sandbox also gets one socket to the launcher, for the companion mod.

{{REQUIRE docs/THREAT_MODEL.md "Recording is possible with audio = \"pulse\""}} {{REQUIRE docs/THREAT_MODEL.md "audio = \"none\" removes the socket"}} {{REQUIRE README.md "audio = \"alsa\" hands the game the raw sound devices (/dev/snd) instead of a server's socket"}} {{REQUIRE README.md "When the launcher adds its companion mod to a Fabric profile, the sandbox also gets one socket to the launcher."}}

In force

  • The root file system is empty and /etc is synthetic: your home directory, /run, /var, /opt and the real /etc do not exist inside.
  • Of one instance, only saves/, logs/ and config/ are writable. mods/, resourcepacks/ and shaderpacks/ are sealed read-only mounts of verified files, and the game's own directory is a scratch directory that is deleted on exit.
  • System calls are allowlisted and everything else is refused. Calls that only an exploit would make kill the process, and the launcher reports that as a sign of compromise.
  • The game cannot run a shell or a downloaded program: only the Java runtime's own files and the dynamic loader may be executed. It has no terminal, no D-Bus, no portal and no agent sockets, and it cannot reach the kernel keyring, where the refresh token rests by default.
  • Once the game runs, the resource limits are read back from the kernel: if they are not in force, the launch says so.
{{REQUIRE README.md "Once the game runs the limits are read back from the kernel: if they are not in force, the launch says so and does not show them as on"}}

Stays open

  • Vulnerabilities in the kernel and in the GPU driver that are reachable through the allowed system calls and ioctls.
  • A mod that executes scripts from config/ can persist inside the sandbox, and a hostile world in saves/ is data the game parses at the next start. bastion-mc launch <id> --burner runs untrusted content on copies that are deleted afterwards.
  • The limits cover memory, swap and the number of tasks. A hostile mod can still fill saves/ and the scratch directory up to the free space of those file systems, and use all CPUs unless you set a quota (cpu_quota_percent).
  • Code in the sandbox can learn the names of host directories, including your user name, from /proc/self/mountinfo. It cannot open them.

03 · What gets out

A filtered network and a credential broker

In the default, filtered network mode the sandbox's network namespace has no route out. The only exits are sockets held by the launcher.

{{REQUIRE docs/THREAT_MODEL.md "Credential broker (filtered mode, on by default)"}}

In force

  • The launcher's DNS responder answers only for allowlisted names and never forwards a query. Its relay passes TCP only to Mojang's service domains on port 443, with a matching SNI, and to the game servers you allowlisted.
  • Multiplayer servers must be allowlisted, in the configuration or for one session with --join. Everything else is unreachable.
  • Voice chat is the only UDP the launcher relays out of the sandbox, and only to a port that a server's rule names, only while a game connection to that server is open and only to the address that connection uses.
  • By default the game does not get your access token. It is given a per-launch placeholder; the launcher's credential broker keeps the real token and attaches it only to an explicit list of Mojang API requests that playing needs.
  • The broker refuses requests from the game to change your skin, cape or name under every configuration.
  • Realms is refused unless you choose how its joins are approved. Then the broker also answers for Realms, and every join waits for an approval you give outside the game, typed into the phone, before the game gets one connection to that Realm's server.
  • Where the token does have to be in the game, it still never touches a command line or the environment.
{{REQUIRE README.md "Voice chat is the only UDP the launcher relays out of the sandbox, and only to a port that a server's rule names"}} {{REQUIRE README.md "Datagrams are relayed to that port only while a game connection to that server is open, and only to the address that game connection is using"}} {{REQUIRE README.md "Realms is refused unless you choose how its joins are approved ([realms] approve). Then the broker also answers for the Realms hosts, and every join waits for an approval you give outside the game before the game gets one connection to that Realm's server"}} {{REQUIRE docs/THREAT_MODEL.md "every join needs an approval given outside the game — a code shown by the launcher, or your authenticator's, typed into the phone"}}

Stays open

  • Code in the game can still ask for what is switched on: the account reads, and one join per game connection it opens to an allowlisted server. That join is not tied to that server: a mod that learns the hash another server is waiting for can authorise a login as you on that other server, once for every game connection it opens.
  • In open network mode, or with network.broker.enabled = false, the token itself is inside the game, and code there can use it or carry it away. The launch log and the front end say so.
  • A server you allowlisted sees whatever the game sends it, and with a voice rule whatever datagrams it sends to that server's voice port. Data can be carried out that way, and the relay cannot tell it from play.
  • With Realms on, code in the game can accept an invitation someone sent you, redeem an invite code it knows, agree to the Realms terms in your name and read your Realms list.
{{REQUIRE docs/THREAT_MODEL.md "A join is spent on a game connection the relay has just opened to an allowlisted server — one join per connection — but it is not tied to that server"}} {{REQUIRE docs/THREAT_MODEL.md "can authorise a login as you on that third server; it can do that once for every game connection it opens"}} {{REQUIRE docs/THREAT_MODEL.md "With a voice rule the same holds for datagrams to that server's voice port"}} {{REQUIRE docs/THREAT_MODEL.md "code in the game can accept a pending invitation (from someone who invited you), redeem an invite code it knows, agree to the Realms terms in your name and read your Realms list"}}

04 · The launcher

The launcher confines itself

The launcher is the part that holds the tokens. It gives up what it no longer needs, and it keeps the window out of its own process.

In force

  • Before it reads anything the game sends, the launcher gives up, on all its threads, writing anywhere but the instance's settings directory, its cache and the directories of the phone's services that are on; program execution; most of the network; and the kernel keyring where the refresh token rests.
  • It makes itself non-dumpable and keeps tokens in locked, self-wiping memory. Where the kernel offers memfd_secret, those pages cannot be read through /proc/<pid>/mem, process_vm_readv or ptrace.
  • The graphical front end is a separate program that holds no token. It starts the launcher and reads its progress events; the protocol between them has no field that could carry a credential, and the launcher binary links none of the front end's dependencies. The one secret it is given is the code of a Realms join that waits for your approval, which is there to be shown to you.
    • {{REQUIRE docs/THREAT_MODEL.md "The launcher binary links no GUI, font or GPU code, and the event protocol has no field that could carry a credential. The one secret it does carry is the code of a waiting Realms approval, which exists to be shown to you"}}
  • If the window is closed or the front end dies, the launcher notices and shuts the game down.
{{REQUIRE README.md "Before it reads anything the game sends, the launcher gives up — on all its threads — writing anywhere but one settings directory of the instance (persist/), its cache and, for the phone's services that are on, the settings-sync directory, the clips folder and the clip buffer"}}

Stays open

  • All of the self-confinement needs Landlock ABI 9, and its file and network part ABI 8. On an older kernel it is partial, and the launcher says what is missing; bastion-mc doctor says what this machine can and cannot enforce.
    • {{REQUIRE README.md "the launcher's own confinement needs Landlock ABI 8 for its file and network part and ABI 9 for all of it (on older kernels it is partial, and said to be)"}}
  • With the broker, the launcher holds the access token for the whole session, and with the phone's services also a Spotify access token and, in totp mode, the Realms TOTP secret. The alternative is the token inside the game, readable by every mod.
    • {{REQUIRE docs/THREAT_MODEL.md "with the phone's services also a Spotify access token and, in totp mode, the Realms TOTP secret — never a refresh token"}}
  • Other software running as you can read the game's memory, read the refresh token from the kernel keyring of the same login session, replace the launcher binary in $PATH or edit config.toml. Root, the kernel, firmware and physical access are out of scope.
  • Whatever can click in the front end's window can start a launch, sign out or trigger scram. That is a problem of integrity, not of confidentiality.

05 · Display and sound

A display of the game's own

X11 lets any client log keys, inject input into other windows and read the clipboard, so handing the game the session's X display would be a way out of the sandbox. The launcher does not do that.

In force

  • On an X11 session the game runs inside gamescope, a nested compositor that itself runs in a sandbox. The game gets a display server of its own and nothing of your session's: no other windows, no keystrokes, and no clipboard in either direction. gamescope would bridge the clipboard, so the launcher loads a cut-off into it, which reports from inside the compositor; without that report the launcher says that the clipboard is not known to be cut. Without gamescope the launch is refused, unless you set allow_x11 = true and accept the risk.
    • {{REQUIRE README.md "gamescope would bridge the clipboard, so the launcher loads a cut-off into it, and that cut-off reports from inside the compositor. Without its report the launcher says that the clipboard is not known to be cut"}}
  • On a Wayland session the launcher asks the compositor for a socket that is marked as sandboxed (wp_security_context_v1), on which a compositor is expected to withhold screen capture, input injection and clipboard-manager access. The protocol only says “should”, so the launcher lists what is offered on that socket itself and says so if a privileged interface it knows is still offered. According to the protocol registry's support table, read on 2026-11-13, KWin (KDE Plasma), Sway, Hyprland, niri, COSMIC, labwc and river implement it.
    • {{REQUIRE README.md "on which a compositor is expected to withhold screen capture, input injection and clipboard-manager access. The protocol only says \"should\", so the launcher connects to that socket itself and lists what is offered there; if a privileged interface it knows is still on offer, it says so"}} {{REQUIRE README.md "read 2026-11-13"}}
  • A sound server that loads modules for its clients is a way out of the sandbox, and PulseAudio and pipewire-pulse do that by default. So with audio = "pulse", the launcher's default, it asks your sound server before each launch and hands the game the audio socket only if the server says no, unless you set allow_pulse_module_loading = true and accept the risk.
    • {{REQUIRE README.md "refuses to hand the game the audio socket unless the server says no"}}

Stays open

  • Mutter (GNOME), Weston and Wayfire do not implement the protocol, according to the same table. There the launcher says so and gives the game the session's socket (with wayland_security_context = "require" it refuses instead); on GNOME that makes the game an ordinary Wayland client of your session.
  • The Wayland path was tested against sway only, headless, and not on a real desktop session. Whether the game is playable inside gamescope has not been assessed.
    • {{REQUIRE docs/THREAT_MODEL.md "Tested against sway only, headless; not on a real desktop session."}} {{REQUIRE docs/THREAT_MODEL.md "Playability inside gamescope (pointer capture, full screen) is not assessed."}}
  • A bug in gamescope or Xwayland that the game can reach yields the compositor's sandbox, and with it the session's display. With allow_x11 = true and no gamescope, the display is a way out of the sandbox.
  • On Wayland the game has the ordinary clipboard while it has focus.
  • With sound enabled, code in the game can record the microphone. Getting a recording out still has to pass the network filter, and where a server rule names a voice port, recorded sound can leave as datagrams to that server. The sound server's answer is checked at launch, not continuously.
  • audio = "alsa" hands the game the raw sound devices: playback and capture of every sound card, with no server to ask and no module-loading check, the most access of the three.
    • {{REQUIRE README.md "playback and capture of every sound card, with no server to ask and no module-loading check, the most access of the three"}} {{REQUIRE docs/THREAT_MODEL.md "where a server rule names a voice port, recorded sound can also leave as datagrams to that server"}}

06 · The account itself

Canary, scram and the runbook

An account is more often lost somewhere else: a phished password, a “verification” app that was given consent. The launcher cannot prevent that; it can notice it and make the response quick.

In force

  • Profile canary. The launcher pins the account's name, skin and cape and compares at every launch. By default, a change that was not made through the launcher stops the launch until you accept it with bastion-mc canary accept.
  • Scram. bastion-mc scram stops running games and removes every credential the launcher keeps from this machine in one step: the sign-ins, the Spotify token, the Realms TOTP secret and the phone browser's profile. It says what it could not remove, and it needs no network.
    • {{REQUIRE README.md "to remove every credential the launcher keeps from the machine in one step — the sign-ins, the Spotify token, the Realms TOTP secret, the phone browser's profile — and to say what it could not remove"}}
  • Runbook. bastion-mc wiki scram prints what to do next, with the exact Microsoft addresses, taken from Microsoft's own help articles. The warning to use another device if this one is in doubt comes first. On this site it is the emergency page.
  • Proofs. bastion-mc export-proofs writes out what the launcher recorded that shows the account is yours, for a dispute with support. It holds only what this launcher saw.

Stays open

  • The canary is a tripwire for visible tampering only: an intruder who just plays trips nothing. Its pin is a file of yours: it guards against the account changing elsewhere, not against software on this machine.
    • {{REQUIRE docs/THREAT_MODEL.md "an intruder who just plays trips nothing"}}
  • Scram revokes nothing at Microsoft or Mojang, and deleted files are not securely wiped; its output says both every time. A token that was copied earlier works until you sign out everywhere, and an issued session token lives up to about 24 hours. That is why the runbook is the second step. Nothing is revoked at Spotify or at the sites the phone's browser was signed in to either.
    • {{REQUIRE docs/THREAT_MODEL.md "Revokes nothing at Microsoft or Mojang"}} {{REQUIRE docs/THREAT_MODEL.md "Nothing is revoked at Spotify"}}
  • The runbook's links were checked on the date given in the file and can go stale. Minecraft's help centre could not be read by a program, so only the existence of its request form was checked. A compromised machine can show a different text.
    • {{REQUIRE docs/THREAT_MODEL.md "only the existence of its request form was checked"}}
  • Nothing in the launcher revokes a session or secures the Microsoft account.

07 · The companion mod and the phone

Interface in the game, decisions outside it

To Fabric profiles of the ten Minecraft versions it was run with, the launcher adds its own companion mod, for one session at a time, as two read-only files outside mods/, which stays exactly what you signed; force = true adds it to the other versions from 1.20.1 to 26.3. It brings the in-game phone, a redone title screen and darker menus. The mod runs inside the game and is not a security feature: the launcher does the deciding.

{{REQUIRE README.md "The launcher adds the mod by itself to Fabric profiles of the ten Minecraft versions it was run with (Minecraft versions; force = true adds it to the other versions from 1.20.1 to 26.3)"}} {{REQUIRE README.md "added for one session at a time as two read-only files outside mods/, which stays exactly what you signed"}} {{REQUIRE README.md "It is a convenience, not a security feature"}}

In force

  • Every command from the phone is parsed strictly, routed to an app of this launch by its exact name, refused unless its verb is in that app's fixed vocabulary, and limited per app and verb, and in all per second. No argument is ever used as a path, an address, a command line or code.
  • What the game cannot get through the phone: a token, a cookie, the browser's profile, the TOTP secret, a path, a web address or a program to run.
  • The services run outside the game's sandbox. The browser, the D-Bus proxy for the Spotify app, the clip recorder and the Realms dialer are started before the launcher confines itself, each in a sandbox of its own; the Spotify token keeper, which holds the Spotify refresh token so that the launcher does not, runs in none. The game reaches none of these programs.
  • The browser shows only the sites you list, each held to its budgets. You sign in to them outside the game, with bastion-mc browser login <site>.
{{REQUIRE README.md "Every command is parsed strictly, routed to an app of this launch by its exact name, refused unless its verb is in that app's fixed vocabulary, and limited per app and verb (and in all, per second); no argument is ever used as a path, an address, a command line or code."}} {{REQUIRE README.md "What it cannot get through the phone: a token, a cookie, the browser's profile, the TOTP secret, a path, a web address or a program to run."}} {{REQUIRE README.md "Each is started before the launcher confines itself, and all but one run in a sandbox of their own"}} {{REQUIRE README.md "The Spotify token keeper is the one helper without a sandbox"}} {{REQUIRE README.md "The game reaches none of these programs."}}

Stays open

  • Whatever is shown on the phone or typed into it is visible to every mod in the game. Type no password into the phone.
  • Whatever an app allows, any code in the game can do, at the rate the launcher allows: control your Spotify playback, open a listed site and act there as you if you are signed in, save, rename or delete clips the launcher saved, type a Realms code, sync settings.
  • Code in the game of one instance can change the synced settings of your other instances: bind a key, change a volume, the field of view, the language.
  • The services that need an account of yours, the Spotify Web API, a signed-in Discord and Realms, have not run against the real services.
{{REQUIRE README.md "Whatever is shown on the phone or typed into it is visible to every mod in the game"}} {{REQUIRE README.md "Type no password into the phone"}} {{REQUIRE README.md "Whatever an app allows, any code in the game can do, at the rate the launcher allows: control your Spotify playback, open a listed site and act there as you if you are signed in, save, rename or delete clips the launcher saved, type a Realms code, sync settings."}} {{REQUIRE README.md "code in the game of one instance can change, through what it leaves in its options.txt, the listed settings of your other instances — bind a key elsewhere, change a volume, the field of view, the language"}}

The front end

The launcher is a command-line program. bastion-mc-gui is an optional window around it, of its own design: a dark instrument panel with a ring gauge around the launch control, and no advertising, news, shop or telemetry. A rail leads to five pages: the launch, with the instance, the stages of a launch and, once the game starts, which protections that launch runs with; the accounts, with sign-in; the instances; a console with the launcher's, the relay's and the game's output; and security, with the emergency panel. While a Realms join waits for your approval, the launch page shows its prompt. The phone's own commands are run in a terminal: the window offers none of them.

How to get it

There are no releases and no binary downloads. bastion-mc is built from its source on Arch Linux with cargo. The PKGBUILD in the repository is a template until there is a release: makepkg builds whatever its source= line points to, not the checkout it lies in. What it needs, in the words of the manual:

Signing in needs an Azure application that you register yourself, because there is no shared client ID, and Mojang has to approve its ID, which can take days. Until then bastion-mc launch <id> --demo starts Mojang's demo mode, with no account and no token.
