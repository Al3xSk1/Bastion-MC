Get started

From the source to a first sandboxed launch

bastion-mc is pre-release software for Arch Linux. You build it from source, and you can try the sandbox in Mojang's demo mode before any account is involved. Signing in needs an application of your own at Microsoft, and its approval by Mojang can take days.

What has been run, and what has not

{{PARAGRAPH README.md "Built and tested on Arch Linux"}}

The sign-in chain (Microsoft, Xbox, Minecraft) and everything that needs a signed-in account are implemented and tested against scripted replies and a stand-in for Mojang. They have not yet been run against the live services, and neither have the phone's services that need an account of yours: the Spotify Web API, a signed-in Discord, Realms. Not exercised on the development machine either, among other things: NVIDIA graphics, a real Wayland desktop session, launching game versions from the Java 8 era, the real age program with its hardware plugins, and coverage-guided fuzzing, which needs a nightly toolchain. The status table in the manual has the details, and the security overview has the threat model's whole list.

Requirements

  • Arch Linux with kernel 6.12 or newer, landlock in the LSM list, and unprivileged user namespaces. Those are the Arch defaults. Newer kernels add more: the launcher's own confinement needs Landlock ABI 8 for its file and network part and ABI 9 for all of it (on an older kernel it is partial, and the launcher says so), and ABI 10, in Linux 7.2, adds rules for UDP.
  • bubblewrap, and for each game version the Java release it declares. The launcher never downloads a Java runtime; it uses only root-owned ones under /usr/lib/jvm. For Java 17 and later it finds only a runtime installed from a jdk package (jdk17-openjdk, jdk21-openjdk, jdk25-openjdk), not from a jre package; for Java 8, jre8-openjdk will do. Minecraft 26.3 needs Java 25. With match = "newer" under [java] in config.toml the launcher takes the lowest installed release at or above the declared one instead. Its own refusal message still suggests the jre package, which does not help for Java 17 and later.
  • On an X11 session: gamescope, which gives the game a display of its own.
  • For the phone's services, if you want them: xdg-dbus-proxy for Spotify, Firefox for its browser, ffmpeg for clips.
  • A systemd user session. It provides the resource limits.
  • For building: cargo, a C compiler (the one Rust links with) and a JDK (javac) of release 17 or newer, because the companion mod is compiled with --release 17.

Build it

Get the source from the repository and build it with cargo.

With cargo

Build in place

cargo build --release
export PATH="$PWD/target/release:$PATH"
bastion-mc --help

The launcher is then target/release/bastion-mc. The commands on this page call it by name, so put that directory on your PATH, as above, or call it by its path; bastion-mc --help lists every command and option. With --workspace the graphical front end is built as well.

{{REQUIRE README.md "cargo build --release leaves the program at target/release/bastion-mc. The commands in this file call it by name, so put that directory on your PATH (or call it by its path)"}}

With makepkg

The Arch packages are a template

packaging/arch/PKGBUILD makes two packages, bastion-mc and bastion-mc-gui. Until there is a release it is a template: it does not build your checkout, and makepkg builds whatever its source= line points to.

On the development machine both packages were built from a tarball of the tree: their check() passes, and both binaries pass the hardening check.

{{REQUIRE README.md "packaging/arch/PKGBUILD does not build this checkout: until there is a release it is a template, and makepkg builds whatever its source= line points to."}} {{REQUIRE README.md "both build, their check() passes and both binaries pass the hardening check — run again on the merged tree of the fourth round, from a git archive of that tree"}}

Settings go in ~/.config/bastion-mc/config.toml, which does not exist until you create it: bastion-mc config example prints a commented template of every key, and bastion-mc config path prints where the file goes.

Before the first launch: display and sound

A launch can be refused for two reasons that are decisions the launcher wants from you. bastion-mc doctor shows which kind of display isolation this machine offers.

Display

Keeping the game off your session's display

X11 lets any client log keys, inject input into other windows and read the clipboard, so handing the game your session's X display would be a way out of the sandbox.

On an X11 session the launcher runs the game inside gamescope, a nested compositor, where the game has a display server of its own. Without gamescope the launch is refused, unless you set allow_x11 = true and accept that risk.

On a Wayland session it asks the compositor for a socket that is marked as sandboxed. Where a compositor lacks the protocol for that, as on GNOME, the launcher says so and uses the session socket; wayland_security_context = "require" refuses instead.

The manual lists the compositors and the options under Display isolation. Only sway was tested, and whether the game is playable inside gamescope (pointer capture, full screen) has not been assessed.

Sound

For sound, your sound server has to refuse module loading

By default PulseAudio and pipewire-pulse let any client ask the server to load modules, and that leads out of the sandbox.

With the default audio = "pulse", the launcher asks your sound server before each launch, and refuses to hand the game the audio socket unless the server says no. To keep sound, switch module loading off once (PipeWire):

mkdir -p ~/.config/pipewire/pipewire-pulse.conf.d
echo 'pulse.properties = { pulse.allow-module-loading = false }' \
    > ~/.config/pipewire/pipewire-pulse.conf.d/90-no-module-loading.conf
systemctl --user restart pipewire-pulse

After that, pactl load-module stops working for everything, which is the point. Otherwise set audio = "none", or allow_pulse_module_loading = true to accept the risk. A third value, audio = "alsa", hands the game the raw sound devices instead of a server's socket: playback and capture of every sound card, with no server to ask and no module-loading check, the most access of the three. With sound on, the game can record your microphone. The manual's section on sound has the details.

Your own sign-in application

There is no shared OAuth client ID, by design. bastion-mc has no central anything: no built-in client ID, no telemetry, no update check. The launcher talks to Microsoft, Xbox Live and Mojang directly, with an Azure application that is yours. You register it once.

  1. In the Azure portal, go to Microsoft Entra ID, then App registrations, then New registration. Supported account types: Personal Microsoft accounts only. Redirect URI: platform Public client/native (mobile & desktop), value http://localhost.

  2. Under Authentication, enable Allow public client flows. Signing in with a device code (bastion-mc login --device) needs it.

  3. Copy the Application (client) ID into ~/.config/bastion-mc/config.toml:

    [auth]
client_id = "xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx"

  4. Ask Mojang to approve the ID. The Minecraft API refuses a new application ID (Invalid app registration) until it is approved: https://aka.ms/AppRegInfo. This can take days. The demo launch below works in the meantime.

bastion-mc config example prints a fully commented configuration file.

The sign-in has been tested against scripted replies only. It has not yet been run against the live Microsoft, Xbox and Mojang services.

The first commands

The first three steps need no account, and they work before Mojang has approved your application.

  1. Check the machine

    bastion-mc doctor

    It checks the kernel, the sandbox and the trust setup, and starts a real test sandbox. It says what this machine can and cannot enforce.

  2. Create an instance

    bastion-mc versions
bastion-mc instance new main --minecraft 26.3

    The first command lists the Minecraft versions in Mojang's manifest. The second creates a vanilla instance with the id main.

  3. Launch it in demo mode

    bastion-mc launch main --demo

    This starts the client in Mojang's own demo mode, with no account; no token exists in that mode. It is a way to test the sandbox on your machine before your application is approved. The first launch fetches the client, its libraries and its assets from Mojang and checks each against the published hashes, and before anything the game prints is shown, the launch says what it set up and what it saw in force. Ctrl-C in the terminal stops the game. On the development machine the real Minecraft client has been run in the sandbox in demo mode, vanilla and as a signed Fabric profile; the status table names the version that was run.

  4. Sign in

    bastion-mc login
bastion-mc status

    login uses the browser and a loopback redirect; bastion-mc login --device uses a device code instead. status shows who is signed in and which instances exist. This is the step that needs your client ID, approved by Mojang, and it is the step that has not yet been run against the live services.

  5. Play

    bastion-mc launch main
bastion-mc launch main --join play.example.org

    Multiplayer servers must be allowlisted: servers = [...] under [network] in config.toml, or in the instance's instance.toml. Everything else is unreachable. --join allowlists one server for this session. Joining a real multiplayer server needs a signed-in session and has not been exercised either; the relay is tested with a stand-in server and with live TLS to Mojang.

Mods, the companion mod and the phone

Mods run only in a signed profile: a Fabric (or Quilt) instance whose mods/ directory is described by a manifest that you sign. The manual's sequence, from a signing key to a launch:

mkdir -m 700 -p ~/secure                           # key generate does not create directories
bastion-mc key generate ~/secure/bastion.key       # ideally kept off this machine
bastion-mc key trust me ed25519:…                  # the public key it printed

bastion-mc profile new perf --minecraft 26.3 --fabric
bastion-mc profile add perf sodium lithium modmenu     # from Modrinth, dependencies included
bastion-mc profile check perf                          # what Modrinth knows about each jar
$EDITOR ~/.local/share/bastion-mc/instances/perf/profile.json    # review it
bastion-mc profile sign perf --key ~/secure/bastion.key
bastion-mc launch perf                 # add --demo until your client ID is approved

profile add takes, for each mod, the newest release that Modrinth lists for the profile's Minecraft version and loader, with what it requires, and checks size and hashes before anything reaches mods/. Nothing is signed: the manifest lists the new jars, and you sign it after you have reviewed it. At launch the signature and every jar are verified, and one extra, missing or modified file aborts the launch. A voice-chat mod needs a rule that names the server's voice port, or it stays silent; the mods page has the rule and every other detail.

{{REQUIRE README.md "For each mod it takes the newest release that Modrinth lists for the profile's Minecraft version and loader, resolves what that build marks as required"}} {{REQUIRE README.md "Nothing is signed."}} {{REQUIRE README.md "one extra, missing or modified file aborts the launch"}} {{REQUIRE README.md "In the default network mode the game has no UDP at all, so such a mod loads but stays silent. To let it talk, name the server's voice port in that server's rule"}}

To a Fabric profile of one of the ten Minecraft versions it was run with, the launcher adds its own companion mod by itself, for that session; force = true under [companion] adds it to the other versions from 1.20.1 to 26.3. In the game, press R, in a world or on the title screen, and the phone slides up with the apps the launcher set up for this launch. Out of the box the Spotify desktop app over D-Bus, its album art and settings sync are on; the browser, the Spotify Web API, clips and Realms approval are off until you switch them on in config.toml, as the phone page describes. Sign in to the browser's sites outside the game, with bastion-mc browser login <site>, and type no password into the phone: every mod in the game can read what you type there.

The graphical front end

bastion-mc-gui is an optional window around the same launcher. A rail on its left leads to five pages: the launch, where you pick the instance, start the game, follow the download and, once the game has started, see which protections that launch runs with; the accounts, where you pick an account and sign in; the instances, where you create one; a console with the launcher's, the relay's and the game's output; and the security page with the emergency functions: scram, the runbook and its links. While a Realms join waits for your approval, the launch page shows its prompt, in code mode with the code. The phone's own commands, browser login, spotify … and realms totp-setup, are run in a terminal: the window offers none of them.

cargo build --release --workspace
target/release/bastion-mc-gui

The first command builds both programs. The front end looks for bastion-mc next to itself, and otherwise in /usr/bin. Building it needs nothing beyond the Rust toolchain; its system libraries are loaded at run time:

pacman -S --needed libxkbcommon ttf-dejavu           # keyboard handling, any TTF font
pacman -S --needed wayland                           # on Wayland
pacman -S --needed libx11 libxcursor libxi libxkbcommon-x11   # on X11
pacman -S --needed vulkan-icd-loader vulkan-radeon   # GPU rendering (or vulkan-intel / nvidia-utils)
pacman -S --needed xdg-utils                         # the "Open link" button

Without a usable Vulkan or OpenGL driver it renders in software; ICED_BACKEND=tiny-skia forces that.

It is a separate program on purpose, not a mode of the launcher:

  • Tokens stay in the launcher process. The protocol between the two programs has no field that could carry one, and the launcher binary links none of the front end's dependencies.
  • The window never waits on the network, the disk or the game. Every launcher command runs in a child process, and progress arrives as messages.
  • If the window is closed, or the front end dies, the launcher notices its control pipe closing and shuts the game down properly. A scram is the exception: the front end never ends the launcher while it removes credentials.
{{REQUIRE README.md "A scram is the exception: the front end never ends the launcher that is removing credentials."}}

What the separation does not cover: the window can still be made to click, for instance to start a launch, to sign out or to trigger scram; and other software running as you, or on X11 any other client, can read the sign-in code off the window, and a Realms approval code while a join waits. The security overview has both under the launcher.

One limit of use: an age vault whose identity asks for a PIN on the terminal cannot be unlocked from the window. Sign in and launch from the command line in that setup.

How it was tested: its tests run without a display, drawn in software and in iced's emulator against a stand-in launcher; a real demo launch was driven through its backend and through the window's own controls; and the real window was started and closed on a private X11 display. Nobody has clicked in a real window, it has not been run on Wayland, and its Realms prompt has never been shown for a real join.
