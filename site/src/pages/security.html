Security overview

The security model in plain language

bastion-mc treats the game as hostile code. The Java process that runs Minecraft is assumed to belong to an attacker from its first instruction, whether through a malicious mod or through something a server sent, and everything around it is arranged on that assumption. That includes the launcher's own companion mod and its in-game phone, which run inside the game.

{{REQUIRE docs/THREAT_MODEL.md "The JVM is treated as hostile from its first instruction — and so is the launcher's own companion mod, which runs in it (J19) — and with it the in-game phone, which is part of that mod"}}

This page is the short version, for a reader who will not go through the whole threat model. The threat model is the authority: for each attack it names the defence and what remains, and for most of them the test or experiment behind the claim. The letters and numbers in brackets on this page, such as J10 or D1, are its rows, and each one is a link to that row.

Pre-release

The tests that the threat model cites pass on the development machine, an Arch Linux system. Several parts have never been run against the live services or on other hardware (what has not been verified), and some things are not defended at all (what is not defended). Read those two sections before you rely on anything here.

What is being protected

  • The Microsoft refresh token. It lives for weeks to months and mints new sessions for the account's Xbox and Minecraft identity. It is the most valuable secret.
  • The Minecraft access token. It lives for 24 hours and lets its holder join servers as you and change your skin and name. It is what “session stealers” take.
  • The signing key for mod profiles, which decides what code may run in a curated instance.
  • Your files and your session: everything in your home directory, the desktop session (keystrokes, clipboard, screen), SSH and GPG agents, browser profiles.
  • The integrity of what runs: client jar, libraries, loader, mods, and in Fabric profiles the launcher's own companion mod.
  • The site sessions of the phone's browser, kept in its profile until you sign out at the site or scram deletes the profile. A signed-in Discord, or any other listed site you signed in to, is a credential: whoever holds it acts as you on that site.
  • The Spotify refresh token, only if you set up the Spotify Web API. It lasts until you revoke the grant. It controls your Spotify playback and devices and reads what is playing; the scopes asked for are playback state and control, nothing of your library.
  • The Realms TOTP secret, only with [realms] approve = "totp". Whoever has it can approve Realms joins.

Threat model, section 1

Who it is defended against

The threat model gives each adversary a letter and uses the letters throughout, so they are kept here.

M · mod

A malicious or compromised mod

Assumed to run arbitrary Java and native code inside the game from the first instruction.

{{REQUIRE docs/THREAT_MODEL.md "Arbitrary Java and native code inside the game JVM from the first instruction."}}

The sandbox exists for this adversary. The layers below are the answer, and each of them leaves something over.

Threat model, section 4.2

S · server or content

A malicious game server, or malicious content

Assumed to send data that makes the game run the attacker's code: Log4Shell-class lookups, deserialisation gadgets, parser bugs. It ends up with the same capability as a malicious mod and meets the same layers.

Two of those classes have a measure of their own as well. The patched logging configuration that Mojang publishes is mandatory and message lookups are off (J14). A filter for the whole Java process rejects deserialisation unless you opt out; mods that install their own filter are the stated remainder (J15).

{{REQUIRE docs/THREAT_MODEL.md "Ends up with the same capability as M."}} {{REQUIRE docs/THREAT_MODEL.md "Mods that install their own stream filter."}}

N · network

A network attacker

Assumed to control DNS answers and to intercept and modify traffic: hostile Wi-Fi, a compromised resolver, BGP. Assumed unable to break TLS 1.3 or to forge certificates from the system trust store.

The launcher speaks TLS 1.3 only, to a fixed list of hosts, without redirects and without plaintext (N1). For Microsoft and Mojang hosts it also pins the keys those services chain to, for the case that a trusted certificate authority issues a certificate it should not have; other hosts, such as the mod loaders' sites, are not pinned unless you pin them (N3).

What remains: denial of service, and being steered to a game server the attacker runs, which is then adversary S (N2). If Microsoft moves to a root outside the pinned list, connections fail until the list is updated or the pins are switched off (N3). And traffic that is recorded today, to hosts that do not negotiate the hybrid post-quantum key exchange the launcher offers first, stays exposed to a future quantum adversary; Microsoft's sign-in hosts were seen to pick a classical one (N1).

C · supply chain

A tampered file

A file altered on a download server or a mirror, or swapped in the local store.

Every Mojang file is checked against the published chain of hashes on download and again at every launch, and a mismatch stops the launch (C1). A modded instance needs your signature over the exact list of mods (C2), and a mod fetched from Modrinth is installed only if it matches the size and hashes the registry lists (C8). What remains: Mojang publishes SHA-1 hashes only (C1); a loader library that has no published hash is trusted on first use when you author a profile (C6); Modrinth's hash and file come from the same party (C8); the launcher itself is built from crates.io dependencies, a risk the threat model calls inherent to using them (C7); and other software running as you can get past several of these checks, as the panel on verified files explains.

O · other user

Another user of the same machine

A different UNIX account. It reads whatever is world-readable: the command line and status of every process, world-readable files, loopback ports.

The game is started with no program arguments at all, and nothing secret is put into its environment, so the token is in neither place (P1, P2). The launcher makes itself non-dumpable, which closes its memory and its descriptors under /proc (P6). For the command-line attack the threat model gives the remainder as “none for O”.

{{REQUIRE docs/THREAT_MODEL.md "none for O"}}

W · web page

A page of a site listed for the phone's browser

Assumed to run any content and script in the phone's browser, on the hosts that site lists, and with a browser exploit to run code as you inside the browser's sandbox.

The browser runs headless in a sandbox of its own, outside the game's, without your home directory, a display, D-Bus or sound, and its only way out is the launcher's relay, which answers only for the hosts of the site that is open (H9, H11). What remains: a compromised browser can change its own profile, which persists into later sessions, and its system-call filter is a deny-list, which leaves more of the kernel in reach than the game's allowlist does (H11).

{{REQUIRE docs/THREAT_MODEL.md "Arbitrary content and script in the in-game browser, on the hosts that site lists; with a browser exploit, code running as you inside the browser's sandbox"}} {{REQUIRE docs/THREAT_MODEL.md "It can change its own profile (site data, service workers), which persists into later sessions"}} {{REQUIRE docs/THREAT_MODEL.md "Kernel bugs reachable from a process under a denylist — more of the kernel than the game's allowlist leaves."}}

U · same-user software

Other software running as you

A process under your own account, outside the sandbox: a compromised editor plugin, an install script.

Not defended. It can read the game's memory, read the refresh token from the kernel keyring of the same login session, replace the launcher binary in your PATH, or edit config.toml. Some things do hold against it: it cannot attach to the launcher or dump it (P6), and with the credential broker the game's memory contains a placeholder instead of the token (P7).

The remedies the threat model names lie outside the launcher: the kernel setting ptrace_scope=3, which closes the reading of the game's memory, or a dedicated UNIX account for gaming. The guide describes both and what each leaves open; neither has been exercised on the development machine.

Out of scope: root, the kernel, firmware, physical access, and Mojang or Microsoft themselves acting maliciously (they can simply hand out a malicious client). The services the phone reaches, Spotify, the sites you list and Realms, are treated like Mojang's: their answers are parsed strictly and bounded, but a service can do whatever it likes with what you gave it, such as your Spotify grant or your session on a site. Threat model, section 2.

The layers, and what each one stops

The game sits behind several mechanisms at once: namespaces set up by bubblewrap, then Landlock, then a seccomp allowlist, all of it inside a systemd scope with memory and task limits. Some of them repeat each other on purpose, and the tests check that: the keyring isolation is tested with each of its two layers alone (J7), and Landlock alone with the system-call filter only logging (J4). The launcher stays outside; it is the part that has to be trusted.

Before the game starts

The game starts from checked files

Mojang's files are checked against the hashes Mojang publishes, and mods against a manifest you signed. Jars and mods are hashed from the very descriptor that is then bound into the sandbox.

{{REQUIRE docs/THREAT_MODEL.md "Jars, asset index, logging config and mods are hashed from the descriptor that is then bind-mounted"}}

Stops

  • A tampered client jar, library or asset, whether it was altered on the download server or in the local store (C1).
  • An unsigned, modified or extra mod. A modded instance exists only by a manifest you signed, and mods/ must match it exactly (C2).
  • A jar from Modrinth that is not the one the registry lists. bastion-mc profile add takes the size and the hashes from the registry's answer and the bytes from its file server only, and installs nothing unless every file matches; what it fetches counts only once you sign the manifest (C8, C2).
  • A malicious Java runtime. Only root-owned runtimes under /usr/lib/jvm are used, and none is ever downloaded (C5).

Does not stop

  • What a mod you signed then does. The signature fixes which files run, not how they behave: a malicious mod is adversary M, and the layers that follow are for it.
  • A bad jar with a matching hash, served by a compromised project account or by the registry itself: the hash and the file come from the same party. A build younger than 48 hours is passed over, which is a delay, not detection (C8, C9).
  • The launcher's own companion mod, the one jar of a Fabric session that is not in your manifest. It is part of the launcher binary, so whoever trusts the launcher already trusts it, and every launch log names it with its SHA-256 (C2).
  • Other software running as you. It can add a signing key of its own unless root-owned keys exist in /etc/bastion-mc/trusted-keys.d (C4), and it can write the file that remembers each instance's last manifest serial, which is what keeps an older manifest from being accepted again (C3). On file systems without fs-verity it can also change a file it can write between the check and the mount (C2).

bubblewrap namespaces

An almost empty machine

The game runs in namespaces of its own, and its root file system starts empty. What is put into it: a read-only /usr, a synthetic /etc, a fresh /proc and /dev, a scratch directory, the saves/, logs/ and config/ of one instance, read-only mounts of the verified mods and packs, in a Fabric profile the launcher's companion mod as two read-only files, and the deliberate holes.

{{REQUIRE docs/THREAT_MODEL.md "In a Fabric profile the launcher's companion mod and its settings are two more read-only files, under /bastion/companion, made for each launch and not kept"}}

Stops

  • Reading your files. Your home directory, /run, /var, /opt and the real /etc do not exist there (J1).
  • Staying on the machine. The game's directory is made for one launch and deleted on exit, and mods and packs reach it as sealed read-only mounts, so a pack that the game or a server drops cannot install itself for the next session (J2).
  • Seeing, signalling or tracing your processes. The game has a process numbering of its own, and there is no D-Bus, no portal and no agent socket inside (J9).

Does not stop

  • Learning the names of host directories, your user name included, from the mount table. The game cannot open them (J1).
  • A mod that executes scripts from config/ persisting inside the sandbox, or a hostile world in saves/ being parsed at the next start. bastion-mc launch <id> --burner runs untrusted content on copies that are deleted (J2).
{{REQUIRE docs/THREAT_MODEL.md "so in-sandbox code can learn host directory names (including the user name in $HOME). It cannot open them."}} {{REQUIRE docs/THREAT_MODEL.md "A mod that executes scripts from config/ can persist inside the sandbox. A hostile world in saves/ is data the game parses on the next start; launch --burner runs untrusted content on copies that are deleted."}}

Landlock

The same limits, enforced a second time

A second set of rules in the kernel, independent of the mounts. It allows only the listed directory trees and adds limits that mounts cannot express.

Stops

  • Starting other programs. Only the Java runtime and the dynamic loader may be executed, so there is no shell and no download-and-run (J3).
  • Creating symbolic links, FIFOs, sockets or device nodes anywhere, together with the system-call filter (J2).
  • Signalling host processes and connecting to their abstract sockets (J9).
  • Network connections other than TCP to the allowlisted ports and, on kernels with Landlock ABI 10, UDP to the launcher's DNS port, and to the launcher's relay sockets on exactly the UDP ports that a server rule names, if one does (J10).

Does not stop

  • Native code inside the Java process itself. That is inherent to a Java runtime with JNI; such code gains nothing the Java process lacks (J3).
{{REQUIRE docs/THREAT_MODEL.md "(Landlock ABI 10) UDP only to the launcher's DNS port, from an ephemeral port — plus, only if a server rule names UDP ports, to the launcher's relay sockets on exactly those ports"}} {{REQUIRE docs/THREAT_MODEL.md "In-process native code is inherent to a JVM with JNI; it gains nothing the JVM lacks."}}

seccomp

A list of permitted system calls

The game may make the system calls on an allowlist. Every other call is answered as if it did not exist. Beside it sits a tripwire: calls that only an exploit would make, such as ptrace or mount, kill the game, and the launcher reports that as a sign of compromise (J6).

Stops

  • Reaching the parts of the kernel that are not on the list, io_uring, userfaultfd, perf_event_open and unshare among them (J4).
  • The x32 route around system-call filters, which would have bypassed a deny-list on Arch kernels (J5).
  • Reading the refresh token from the kernel keyring. The filter denies the keyring calls, and independently of that the sandbox starts in a fresh session keyring (J7).
  • Injecting keystrokes into the terminal that started the launcher. The sandbox has no terminal at all, and the filter refuses the call as well (J8).

Does not stop

  • Bugs in the system calls that are allowed, and in the graphics driver's interface (J4).
{{REQUIRE docs/THREAT_MODEL.md "Bugs in allowed syscalls and in the GPU driver ioctl surface."}}

Network namespace and relay

No route out, except through the launcher

In the default, filtered network mode the sandbox has a private network namespace with no route. The only exits are sockets that the launcher holds: a DNS responder and a relay, both working from an allowlist.

Stops

  • Sending data to an attacker's host. Names that are not allowlisted do not resolve, and TCP is relayed only to Mojang's service domains on port 443 with a matching server name, and to the game servers you allowlisted (J10).
  • Smuggling data out in DNS queries. The responder never forwards one (J11).
  • Reaching your router or services on 127.0.0.1. The relay refuses private, loopback and link-local targets unless you allow them (J12).
  • Using voice chat as a way out. UDP is relayed only where a server's rule names UDP ports, and then only to such a port of that server, only while a game connection to it is open, and only to the address that connection uses; without such a rule no UDP socket exists (J20).

Does not stop

  • Covert channels through what is allowed. A game server you allowlisted sees whatever the game sends it, and that cannot be told apart from play. With a voice rule the same holds for datagrams to that server's voice port (J10, J20).
  • Code in the game opening a game connection by itself. A connection is not proof that you are playing: code can open one to an allowlisted server, keep it for as long as the server lets it idle, and send datagrams to that server's voice port within the limits (J20).
  • A request inside TLS that names another host than the connection does. A relay that does not terminate TLS cannot see it; the large content networks reject such a mismatch (J12).

The price: LAN discovery and everything else over UDP do not exist in the sandbox, and Realms joins are refused unless you choose how they are approved (Realms).

All of this is filtered mode. The two other modes: with none the game has a network namespace with nothing in it, as a --burner session always has; with open it has the host's network, with no relay, no allowlist and no credential broker, so the token goes into the game and services on the host's loopback are reachable. Nothing on this panel is claimed for open mode; see also the broker.

systemd scope

Limits on memory and tasks

The whole sandbox runs in a systemd scope with a memory ceiling, no swap and a limit on the number of tasks. A ceiling on CPU time is optional (cpu_quota_percent). The limits come from your systemd user session. Once the game runs they are read back from the kernel: if they are not in force, the launch says so and does not show them as on, and sandbox.cgroup = "require" stops it.

{{REQUIRE README.md "Once the game runs the limits are read back from the kernel: if they are not in force, the launch says so and does not show them as on (cgroup = \"require\" stops it)."}} {{REQUIRE README.md "A systemd user session provides the resource limits."}}

Stops

  • Runaway use of memory and runaway numbers of processes and threads. The game is killed inside its own group.

Does not stop

  • Filling saves/ and the scratch directory up to the free space of those file systems.
  • Using all CPUs, unless you set a quota.

Threat model, section 5, item 6

The launcher

The trusted part hardens itself

The launcher handles the tokens. It keeps them only in locked memory that wipes itself, and it makes itself non-dumpable. Before it reads anything the game sends, it gives up, on all its threads: writing anywhere but the instance's settings directory, its cache and the directories of the phone's services that are on; reading anything but /etc, /usr, /proc and the name resolver's configuration; program execution; most of the network; and the kernel keyring where the refresh token rests. All of that needs Landlock ABI 9. On an older kernel the launcher applies what it can and says what is missing, and launcher.confine = "require" refuses to launch instead.

{{REQUIRE README.md "Before it reads anything the game sends, the launcher gives up — on all its threads — writing anywhere but one settings directory of the instance (persist/), its cache and, for the phone's services that are on, the settings-sync directory, the clips folder and the clip buffer; reading anything else but /etc, /usr, /proc and the name resolver's configuration; program execution; most of the network; and the kernel keyring where the sign-in token rests"}} {{REQUIRE README.md "The whole of it needs Landlock ABI 9. On an older kernel launcher.confine = \"auto\" applies what it can and says what is missing — in the launch log, in doctor and in the front end —, and \"require\" refuses to launch."}}

Stops

  • Another process attaching to the launcher, or dumping it, to read tokens (P6).
  • The token appearing on the game's command line, in its environment or in a core dump. The game is started without program arguments, its environment is built from scratch, and the kernel is made to abort a core dump (P1, P2, P8).
  • A bug in what the launcher reads from the game, or from the phone's helpers, becoming code with the launcher's full rights: it has confined itself before it reads any of that (J18).
  • A bug in the window toolkit, in text shaping or in a graphics driver being used to read tokens. The graphical front end is a separate process in which tokens never exist (G1).
{{REQUIRE docs/THREAT_MODEL.md "The launcher confines itself before it reads any of that, on every thread."}}

Does not stop

  • Root, code in the kernel, and cold-boot attacks (P6).
  • What a launcher taken over through such a bug would still have: the session's access token, UDP, TCP to any host on the allowed ports and signals to all your processes; with the phone's services also the browser's remote control, a Spotify access token, the Realms TOTP secret in totp mode and up to 8 connections through the Realms dialer (J18, H23).
  • The front end being made to click, for instance to start a launch, to sign out, or to trigger scram, after which you have to sign in again. That is a problem of integrity, not of confidentiality (G1, G6).
  • Other software running as you, or on X11 any other client, reading the sign-in code or link off the window or injecting clicks into it. The code and the link are useless without your Microsoft credentials; a Realms approval code, which the window shows while a join waits, is not useless: it approves that join (G5).

How the token, or its placeholder, reaches the game

The deliberate holes: display, sound, graphics

A game needs a window, sound and the graphics card. These are the openings in the sandbox. Each one is narrowed, and each one keeps a remainder. For sound the setting audio decides the opening: "pulse", the default, hands over a sound server's socket after asking the server; "none" removes the sound hole; and "alsa" hands over the raw sound devices, the most access of the three.

Display · X11

A display server of the game's own

X11 lets any client log keys, inject input into other windows and read the clipboard, so handing the game your session's display would be a way out of the sandbox. On an X11 session the launcher runs the game inside gamescope, a nested compositor that runs in a sandbox of its own.

Stops

  • The game seeing your other windows or your keystrokes (D1).
  • The clipboard crossing in either direction. gamescope would bridge it, so the launcher loads a cut-off into gamescope, and claims the cut only when the cut-off reports from inside the compositor; without that report it says that the clipboard is not known to be cut (D1).

Does not stop

  • A bug in gamescope or Xwayland that the game can reach. It yields the compositor's sandbox, which holds your session's display (D1).
  • Another way of moving a selection that a build of gamescope might have. The report shows that the bridge's calls land in the cut-off; that gamescope has no other way was tested for gamescope 3.17 as Arch packages it, and for nothing else (D1).
  • Anything, once you set allow_x11 = true and gamescope is absent. The game is then a client of your session's X server, and that is a way out of the sandbox. Without gamescope and without that setting the launch is refused (D1).

Whether the game is playable inside gamescope (pointer capture, full screen) has not been assessed.

Display · Wayland

One socket, after the server has been asked

So before each launch the launcher asks your sound server to load a module that does not exist, and hands over the socket only after a clean refusal. With audio = "none" the game gets no socket at all. With audio = "alsa" it gets the raw sound devices (/dev/snd) instead: no server to ask and no module-loading check, playback and capture of every sound card.

Stops

Does not stop

What the credential broker changes

Playing needs a handful of requests to Mojang's API that carry your access token; joining a server is one of them. Ordinarily the game holds the token and makes those requests itself, and then every mod in the game can read the token.

With the credential broker, which is on by default in filtered network mode, the game is given a placeholder that is made for one launch. The launcher keeps the real token. It answers the game's HTTPS connections to Mojang's API itself, with a certificate authority that exists for one session and only in the sandbox's trust store, and attaches the real token only to requests on an explicit list (J13):

  • joining a server, the chat-signing key, and reads of the account; friends, settings, reports and telemetry are separate switches and off by default;
  • everything that would change something and is not on the list is refused, and changes of skin, cape and name are refused under every configuration;
  • a join is honoured once per open game connection that the relay carries, for the session's own profile, and the launcher rebuilds the forwarded request itself;
  • replies that contain the token are withheld, and so is a reply to a request with the token that arrives in an encoding, because it could not be checked;
  • everything the broker holds in memory for the game comes out of one budget for all connections.

Realms is brokered the same way once you choose how its joins are approved; Realms below says what changes.

What that buys

  • Nothing in the game can change your skin, cape or name, or carry the token away.
  • Software running as you that reads the game's memory finds a placeholder there, not the token (P7).

What remains, and what it costs

  • Code in the game can still ask for what is switched on: the reads of the account, and server joins. A join is spent on a game connection that the relay has just opened to a server you allowlisted, one join per connection, but it is not tied to that server: a mod that learns the hash some other server is waiting for, over chat on an allowlisted server for instance, can authorise a login as you on that other server, once for every game connection it opens. Without at least one allowlisted game server no join is honoured. Removing this needs a proxy for the login protocol, which is not built (J13, section 8).
  • The launcher now holds the access token for the whole session, in secret memory and in a process that has confined itself, and with the phone's services also a Spotify access token and, in totp mode, the Realms TOTP secret, never a refresh token. Without the broker it would hold no credential while the game runs (section 6).
  • In open network mode, or with network.broker.enabled = false, the token itself is in the game. The launch log and the front end say so (J13).
  • The broker is tested against a stand-in for Mojang's API and a real sandboxed Java process. It has not been run against the real Mojang API.

The channel and the dispatcher

A fixed vocabulary per app, and rate limits

The phone's commands reach the launcher over the companion's one socket, and the launcher reads them only after it has confined itself.

Stops

  • A command an app does not have, or one beyond its rate. Every command is parsed strictly, routed only to an app of this launch by its exact name, refused unless its verb is in that app's fixed list, and refused when that verb's budget is empty; all connections together are limited per second as well (H1).
  • Paths, addresses, URLs, command lines and code: no argument of a command is ever used as one (H1).
  • Secrets reaching the game. What the launcher sends the phone is state for display, pictures and short notices, never a token, a cookie, the browser's profile or the TOTP secret (H3).

Does not stop

  • Any code in the game sending any command an app accepts, at the rate it accepts. The vocabulary and the limits are the defence, not the sender's identity, which does not exist (H1).
  • Any code in the game taking the phone's connection over, reading everything the launcher sends the phone, or drawing a fake phone or a fake prompt (H1, H5).
  • A bug in the frame reader or the dispatcher. That would be a bug in the trusted base, like one in the DNS or SNI parser; both are small, driven by generated input, and run in the confined launcher (H1).

What is not defended

These are the sixteen points of section 5 of the threat model, in the same order and in plainer words. The list in the threat model is the authoritative one.

  1. Other software running as you. Anything else under your account can read the game's memory, read the refresh token from the kernel keyring of the same login session, replace the launcher binary in your PATH, or edit config.toml. That includes the age vault: a hardware-backed identity makes a copy of the vault file useless without the device, but such software can ask the connected device to decrypt, and it can add a recipient to a recipients file of your own, so that the next stored token is encrypted to it as well. Only a root-owned /etc/bastion-mc/age-recipients takes the recipients out of its reach, and that closes this quiet variant and nothing more: software that puts itself between you and the launcher has the token the moment you launch. A launcher that runs as you cannot defend you from yourself; a dedicated UNIX account for gaming can (P7, the guide).
  2. An X11 session without gamescope, once allow_x11 is set. The game is then a client of your session's X server. With gamescope it is on a display of its own (D1).
  3. The session token inside the game when the broker is not in use: open network mode, or network.broker.enabled = false. With the broker, what remains is that code in the game can request what is switched on: reads of the account, and one join per game connection it opens, which is good for a login on any server, not only the one the connection goes to (J13).
  4. The microphone, while Pulse audio is enabled. The game can record, and where a server rule names a voice port, recorded sound can also leave as datagrams to that server. Loading modules through the same socket is closed: the launcher refuses the socket unless the server denies module loading (D3, J20).
  5. Vulnerabilities in the kernel and in graphics drivers that can be reached through the system calls and device calls the game is allowed to make (J4, D4).
  6. Denial of service, partly. Memory, swap and the number of tasks are limited, and CPU time can be; the limits are read back from the kernel once the game runs, and sandbox.cgroup = "require" stops a launch whose limits are not in force. A hostile mod can still fill saves/ and the scratch directory up to the free space of those file systems, and use all CPUs unless a quota is set. On the launcher's side, its logs, its connections and what it holds in memory for the game are bounded; the companion channel, the phone with its services and the voice relay have bounds of their own; and the phone's helpers have resource limits of their own where the game's are in use, the browser's read back from the kernel and the clip recorder's only asked for.
  7. Realms and UDP. Realms joins are refused unless you set [realms] approve, which is off by default. Then Realms is brokered, and every join needs an approval given outside the game: a code shown by the launcher, or your authenticator's, typed into the phone; a launch without a phone refuses Realms approvals up front. None of it was tried against the real Realms service, and a Realm with a resource pack probably fails to join. Apart from name lookups, which the launcher's own DNS responder answers inside the sandbox, UDP exists only as datagrams relayed to the ports that a server rule names, for voice chat, which gives point 8 a datagram form; LAN discovery and everything else over UDP do not exist in the sandbox (J21, J22, J20, J10).
  8. Covert channels to an allowlisted server. Whatever the game may send to a server you allowlisted can carry data out. The relay sees an encrypted stream and cannot tell (J10).
  9. Hardware fingerprinting. Host name, machine id and network interfaces are synthetic or absent, but the graphics card's renderer string, the CPU model in /proc/cpuinfo and the amount of memory are the real ones.
  10. The account at Microsoft. Nothing here revokes a session or secures the Microsoft account. What the launcher offers is about noticing and reacting.
  11. The companion mod is not a defence. Any other mod in the same game can change it, imitate it or switch it off, and any program running as you that can edit config.toml can change its settings. Nothing in the threat model relies on it, and nothing it shows in the game can be trusted more than the game itself, the phone included (J19, the companion mod).
  12. Server rules. Fullbright, off by default, is forbidden on some servers, and the launcher knows nothing about any server's rules; a server may have rules about zoom and the HUD read-out too. The mod sends nothing to a server and leaves no trace in the protocol, which also means that a server cannot be shown that it is harmless.
  13. A mod that is malicious as published. profile add and profile check say what the registry lists, not what a jar does, and profile audit says what a jar's classes name, not what they will do. The decision to run a jar is your signature; what contains it is the sandbox (C8 to C12, section 4.2).
  14. The in-game phone is interface only. What it shows and what you type into it is visible to every mod in the game, and any code in the game can do whatever the phone can do; type nothing secret into it. Its clock shows the game's time zone, which is UTC unless you set [sandbox] expose_timezone = true (H2 to H5).
  15. The phone's browser while it runs. Whatever can drive the phone can act as you in a page where you are signed in; the launcher keeps the browser to the sites you listed and within their budgets, not to what you meant to do there. The sign-in window of bastion-mc browser login <site> is an ordinary client of an X11 display. The browser is off by default (H8, H13).
  16. Versions within a family that were not started. The companion mod assumes that every Minecraft version of a family behaves like the one version of it that was run: their stand-ins are identical by construction, their behaviour was not observed (the companion mod).

Notice

The profile canary

The launcher pins what the account looks like (name, skin, cape) and compares it at every sign-in, before the token is used for anything. By default a change that was not made through the launcher stops the launch until you accept it with bastion-mc canary accept.

Its limits: it is a tripwire for visible tampering only, and an intruder who just plays trips nothing. The pin is a file of yours, so it guards against the account changing elsewhere, not against software on this machine (A1).

React

Scram

bastion-mc scram first stops whatever could still store a credential: running launches, with the phone's helpers, pending sign-ins and the Spotify token keeper. Then it removes the credentials: every refresh token in the kernel keyring and every vault file, and in a full run also the Spotify refresh token and the Realms TOTP secret. Every run deletes the phone browser's profile with its record of sign-ins, unless a bastion-mc browser login <site> window still holds it. What it could not do or confirm is a line starting COULD NOT, and its exit status is then 1. It needs no network.

Its limits: it revokes nothing at Microsoft or Mojang, and deleted files are not securely wiped; its output says both every time. A token that was copied earlier works until you sign out everywhere, and a session token that was already issued lives for up to about 24 hours. Nothing is revoked at Spotify or at the sites the browser was signed in to either: they keep the session until you sign out there. Removing the Spotify and TOTP keys was never run against a real keyring (A2).
