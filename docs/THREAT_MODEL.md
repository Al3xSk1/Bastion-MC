# bastion-mc threat model

This document says what the launcher defends, against whom, with which mechanism, and how
each claim is checked. It also says, without softening, what is **not** defended. Where a
row cites a test, that test lives in this repository and passes on the development machine
(Arch Linux, kernel 7.2, Landlock ABI 10, bubblewrap 0.13.1, OpenJDK 27).

## 1. Assets

| Asset | Lifetime | Why it matters |
|---|---|---|
| Microsoft **refresh token** | weeks–months | Mints new sessions for the Microsoft account's Xbox/Minecraft identity. The most valuable secret. |
| Minecraft **access token** | 24 h | Lets its holder join servers as you and change skin/name. What "session stealers" take. |
| **Signing key** for mod profiles | long | Decides what code may run in a curated instance. |
| The **user's files and session** | — | Everything in `$HOME`, the desktop session (keystrokes, clipboard, screen), SSH/GPG agents, browser profiles. |
| **Integrity of what runs** | — | Client jar, libraries, loader, mods — and, in Fabric profiles, the launcher's own companion mod. |
| The in-game browser's **site sessions** (its profile) | until you sign out at the site, or `scram` deletes the profile | A signed-in Discord, or any other listed site you signed in to, is a credential: its holder acts as you on that site (rows H8–H13). |
| **Spotify refresh token** (only with the Web API set up) | until you revoke the grant | Controls your Spotify playback and devices and reads what is playing; the scopes asked for are playback state and control, nothing of your library (H15, H19). |
| **Realms TOTP secret** (only with `[realms] approve = "totp"`) | until replaced | Whoever has it can approve Realms joins (J22). |
| The account's **Xbox identity in the Bedrock game** (only if you play Bedrock, §4.8): a refresh token of the Microsoft account for Minecraft for Android (client `0000000048183522`, Xbox user-auth scope), the key the game made to sign its Xbox requests, Xbox and Minecraft tokens | the refresh token: weeks–months. On this machine: one session — in the game's memory, and in the session's data directory until it is deleted (end of the session; after a crash, the next Bedrock start or `scram`) | Its holder can join servers and Realms as you (with the owner's rights on your Realms), spend your Minecoins on Marketplace items, change your Bedrock character and cape, act on your Xbox friends and presence — and possibly (not verified) obtain a Java token. Unlike the Java tokens, **the game holds it**: nothing can broker it (B15). |

## 2. Adversaries

| ID | Adversary | Capability assumed |
|---|---|---|
| **N** | Network attacker | Controls DNS answers and can intercept/modify traffic (hostile Wi-Fi, compromised resolver, BGP). Cannot break TLS 1.3 or forge certificates from the system trust store — except in row N3. |
| **M** | Malicious or compromised mod | Arbitrary Java **and native** code inside the game JVM from the first instruction. |
| **S** | Malicious game server / content | Sends data that triggers a JVM-side RCE (Log4Shell-class lookups, deserialisation gadgets, parser bugs). Ends up with the same capability as **M**. |
| **O** | Other local user | A different UID on the same machine. Reads everything world-readable: `/proc/*/cmdline`, `/proc/*/status`, world-readable files, loopback ports. |
| **U** | Same-user software | A process running as *your* UID outside the sandbox (a compromised editor plugin, an npm post-install script). |
| **C** | Supply chain | A tampered file on a CDN/mirror, or a swapped file in the local store. |
| **W** | A web page of a site listed for the phone's browser, or whoever controls one | Arbitrary content and script in the in-game browser, on the hosts that site lists; with a browser exploit, code running as you inside the browser's sandbox (rows H8–H14). |

For Bedrock (§4.8): **S** also means a hostile Bedrock server, Realm, event server or add-on.
Bedrock is native C++ with a script engine for add-ons; a memory-safety bug there gives
native code in the game, the capability of **M**. **M** is native code loaded by
mcpelauncher's own mod loader, which gets no mods directory (B9, B12). **C** also means the
`mcpelauncher-client` build — about thirty repositories, built from the AUR on your machine,
whose manifest downloads its HTTP library (curl) without a checksum (B3) — and the game
files imported from `mcpelauncher-ui` (B5).

Out of scope: root, the kernel, firmware, physical access, and Mojang/Microsoft themselves
acting maliciously (they can simply hand out a malicious client). The services the phone
reaches — Spotify, the sites you list, Realms — are treated like Mojang's: their answers
are parsed strictly and bounded, but a service can do with what you gave it (your Spotify
grant, your session on a site) whatever it likes.

## 3. Trust boundaries

```
 ┌──────────────────────────── host, your UID ────────────────────────────────┐
 │                                                                            │
 │  bastion-mc (launcher)            non-dumpable, no_new_privs, RLIMIT_CORE=1│
 │  ├─ auth: MSA → XBL → XSTS → MC   tokens only in locked, self-wiping pages │
 │  │                                (memfd_secret where the kernel has it)   │
 │  ├─ verified store                every file hashed; bound into sandbox by │
 │  │                                the descriptor that was hashed           │
 │  ├─ egress relay + DNS responder  holds the ONLY sockets that lead out     │
 │  │                                (UDP: only to voice ports a rule names)  │
 │  ├─ credential broker             terminates the game's TLS to Mojang's API│
 │  │                                (and Realms', once you set approvals up) │
 │  │                                and holds the access token: the game has │
 │  │                                a placeholder                            │
 │  ├─ log relay                     sanitises every byte from the sandbox    │
 │  ├─ companion channel             logs what the companion mod reports;     │
 │  │                                carries the phone's commands in and its  │
 │  │                                state and pictures out                   │
 │  └─ phone dispatcher              per-app vocabulary and rate limits; holds│
 │                                   no secret                                │
 │  helpers, started before the launcher confines itself, each in a sandbox   │
 │  of its own: headless Firefox (the phone's browser; out only through the   │
 │  launcher's relay), xdg-dbus-proxy (the Spotify app's MPRIS and nothing    │
 │  else), the clip recorder (reads the game's display), the Realms dialer;   │
 │  outside any sandbox: the Spotify token keeper (Spotify's refresh token)   │
 │        │ fd 0: AF_UNIX socketpair (launch frame; placeholder, not token)   │
 │   before it reads anything from the game the launcher confines ITSELF      │
 │   (Landlock + a system-call filter, on all its threads)                    │
 │ ═══════╪══════════ user ns ▸ user ns ▸ pid/ipc/uts/cgroup/mount/net ns ════│
 │        ▼                                                                   │
 │  bwrap ─▶ init stage ─▶ JVM       Landlock + seccomp(allowlist+tripwire)   │
 │  empty tmpfs "/"; ro /usr; synthetic /etc; fresh /proc,/dev; no route      │
 │  rw: /game (scratch) + saves/ logs/ config/ of ONE instance                │
 │  ro: mods/ resourcepacks/ shaderpacks/ (verified files, sealed tmpfs)      │
 │  ro: /bastion/companion (the launcher's companion mod, Fabric only)        │
 │  holes: 1 display socket (the game's own: security context or nested       │
 │  compositor), 1 audio socket (or /dev/snd with audio = "alsa"), /dev/dri   │
 │  (+ its sysfs dir); Fabric profiles: 1 socket to the launcher (the         │
 │  companion channel: the mod's reports and the phone's commands in, the     │
 │  phone's state and pictures out)                                           │
 │  the whole sandbox sits in a systemd scope: memory, no swap, task limit    │
 └────────────────────────────────────────────────────────────────────────────┘
```

The JVM is treated as hostile from its first instruction — and so is the launcher's own
companion mod, which runs in it (J19) — and with it the in-game phone, which is part of
that mod (§4.7). The launcher is the trusted computing base: about 74k lines of Rust
including its unit tests (59k before the fifth round added Bedrock, 38k before the phone's
services were added). `unsafe` appears
only around raw system calls and the descriptors they hand over, the locked-memory
mapping, the wiping allocator, and the two places that fork: the fork/exec hook and the
browser's stage, which starts Firefox. The helpers the phone's services start (§3, §4.7)
run this program or a distribution program in a sandbox of their own — except the Spotify
token keeper, which has to reach the token store (§6).

In a Bedrock session the process in the sandbox is `mcpelauncher-client`, which loads the
game's `libminecraftpe.so` with its own linker; the game's data directory is per-session
scratch, the client's sign-in window is replaced by the launcher's stub (the launcher binary
itself), and the launcher holds no credential of its own during that session — no Java
token, no token store, no vault; with Realms joins brokered, only the game's own tokens on
the requests it forwards (§4.8, B32).

The **graphical front end** (`bastion-mc-gui`) is deliberately *not* part of that base. It
is a different program in a different process: it starts the launcher with `--events` and
reads typed progress events from its standard output (§4.5). The launcher binary links no
GUI, font or GPU code, and the event protocol has no field that could carry a credential.
The one secret it does carry is the code of a waiting Realms approval, which exists to be
shown to you (J22). In a Bedrock session it also carries, the other way, what you answer the
launcher's prompts with: a Realms code, or the address a Microsoft sign-in ended on, whose
code is single-use and worthless without the verifier the game holds (B20, B23).

## 4. Attack surface matrix

"Verified by" names a test (`tests/…` or a unit test) or an experiment in §7.

### 4.7 The in-game phone and its services

In a Fabric instance the companion mod has a phone (`docs/PHONE.md`): apps for Spotify, a
web browser (and Discord in it), clips, Realms approvals and settings sync, drawn by the mod
in the game and served by the launcher over the companion channel (protocol 2). The phone is
code inside the game, so everything here assumes that **any code in the game can do what
the phone can do**: what keeps that from mattering is the launcher's side — a fixed
vocabulary per app, rate limits, budgets, and secrets that never enter the game. The
services run in the launcher (after it has confined itself) and in helpers of their own,
each started before the confinement (§3). Spotify, clips and the browser are prepared only
when there is a phone to serve — the companion added to the instance with its channel, and
its phone switched on; settings sync does not need one, and a launch without one refuses
Realms approvals up front (J21–J24).

### 4.8 Minecraft: Bedrock Edition (the Android build)

bastion-mc runs the user's installed `mcpelauncher-client` on game files the user downloaded
with `mcpelauncher-ui` from their own Google Play purchase (`docs/BEDROCK.md`). The difference
from Java that everything below follows from: **the game's own sign-in library needs the
account's Xbox identity, so the game holds it**. The launcher cannot keep it out (as the
credential broker does on Java); it limits where the game can send it, keeps it for one
session only, keeps sign-in pages and Java credentials out of the game, and removes what is
left. None of this has run with the real client or game: every row was verified against
stand-ins (a stand-in client the tests compile and start in the real sandbox, stand-in
versions, servers, services and sign-in addresses; §7 E33 to E37).

## 5. Not defended — read this before relying on it

1. **Other software running as you (U).** It can read the game's memory (P7), read the
   refresh token from the kernel keyring (same login session), replace the launcher binary
   in `$PATH`, or edit `config.toml`. That includes the **age vault**: a hardware-backed
   identity makes a *copy* of the vault file useless without the device, but it does not
   stop such software from asking the connected device to decrypt (a touch or PIN policy
   on the device is all that stands in the way), and it has no say over the *recipients* —
   a recipients file of your own can be extended, and the token stored at the next launch
   is then encrypted to the added recipient too, without any touch. Only a root-owned
   `/etc/bastion-mc/age-recipients` takes the recipients (and the choice of store) out of
   its reach; `doctor` says which case applies. That file closes the quiet, lasting
   variant — one line added once — and nothing more: software that puts itself between you
   and the launcher (another `bastion-mc` earlier in `$PATH`, a wrapper, a preloaded
   library) has the token in the moment you launch, whatever the vault is encrypted to.
   On this development machine the account is also in
   the `docker` group, which makes any same-user process root-equivalent. A user-level
   launcher cannot defend the user from themself; a dedicated UNIX account for gaming can
   (`MC_VAULT_ACCOUNT.md`).
2. **X11 sessions without gamescope** once `allow_x11` is set (D1). With gamescope the
   game is on a display of its own.
3. **The session token inside the JVM** when the broker is not in use: `open` network mode
   or `network.broker.enabled = false` (J13). With the broker, what remains is that code in
   the game can request what is switched on: account reads, and one join per game connection
   it opens — a join that is good for a login on *any* server, not only the one the
   connection goes to (J13).
4. **Microphone** with Pulse audio enabled (D3); where a server rule names a voice port,
   recorded sound can also leave as datagrams to that server (J20). (Module loading through
   the same socket is closed: the launcher refuses the socket unless the server denies it.)
5. **Kernel and GPU-driver vulnerabilities** reachable through allowed syscalls/ioctls.
6. **Denial of service, partly**: memory, swap and the number of tasks are limited by a
   systemd scope (the game is killed inside its own group; the limits are read back from
   the kernel once the game runs, and `sandbox.cgroup = "require"` stops a launch whose
   limits are not in force), and CPU time can be (`cpu_quota_percent`). A hostile mod
   can still fill `saves/` and the scratch directory up to the free space of those file
   systems, and use all CPUs unless a quota is set. On the launcher's side: its log is
   bounded per source (the game cannot crowd the relay's or the launcher's lines out of
   it), the number of launch logs and of relay connections is bounded, and what the
   credential broker holds in memory for the game is bounded at 64 MiB in all. Not under
   that budget: the texture gateway, which holds up to 4 MiB per connection while a
   texture is fetched and handed over (at most 256 connections). The companion channel, the
   phone and its services, and the voice relay have bounds of their own (J19, H1, H8, H15,
   H16, J20). The phone's helpers have resource limits of their own where the game's are
   in use (the browser's read back from the kernel, the clip recorder's only asked for).
7. **Realms and UDP**: Realms joins are refused unless `[realms] approve` is set (it is
   `"off"` by default); then Realms is brokered (J21) and every join needs an approval
   given outside the game — a code shown by the launcher, or your authenticator's, typed
   into the phone (J22); a launch without a phone refuses Realms approvals up front. None of
   it was tried against the real Realms service, and a Realm with a
   resource pack probably fails to join (the pack's address is not reachable from the
   sandbox). Besides the questions to the launcher's own DNS responder (J10), UDP exists
   only as relayed datagrams to the UDP ports that a server rule names (voice chat, J20) — which gives item 8 a datagram form —; LAN discovery and
   everything else over UDP does not exist in the sandbox. A Bedrock session is the
   exception on both counts (§4.8): it has no phone, and takes the code of a Realms or
   event-server join at the terminal or in the front end (B31); and its game's datagrams
   (RakNet) go to the Bedrock servers you listed and to a server whose join you approved
   (B29), which gives item 8 the same datagram form there. LAN games and NetherNet are
   refused in a Bedrock session too (B35).
8. **Covert channels to an allowlisted server.** Whatever the game may send to a server you
   allowlisted can carry data out; the relay sees an encrypted stream and cannot tell.
9. **Hardware fingerprinting.** Host name, machine id and network interfaces are synthetic
   or absent, but the GPU's renderer string, the CPU model in `/proc/cpuinfo` and the
   amount of memory are the real ones.
10. **The account at Microsoft.** Nothing here revokes a session or secures the Microsoft
    account; §4.6 is about noticing and reacting.
11. **The companion mod is not a defence.** It can be changed, imitated or switched off by
    any other mod in the same JVM, and its settings by any program running as you that can
    edit `config.toml` (item 1). Nothing in this document relies on it, and nothing it shows
    in the game can be trusted more than the game itself (J19, `COMPANION.md`). That
    includes the phone (item 14).
12. **Server rules.** Fullbright (off by default) is forbidden on some servers, and the
    launcher knows nothing about any server's rules. Zoom magnifies what the game already
    draws, and the HUD read-out repeats what the game's debug screen shows (and is withheld
    with it under reduced debug information) — a server may have rules about those too. The
    mod names no networking API beyond the socket to the launcher (a test scans its class
    files), so it sends nothing to a server and leaves no trace in the protocol — which
    also means that a server cannot be shown that it is harmless.
13. **A mod that is malicious as published.** `profile add` and `profile check` say what
    the registry lists, not what a jar does (C8–C12); `profile audit` says what a jar's
    classes name, not what they will do. The decision to run a jar is your signature; what
    contains it is §4.2.
14. **The in-game phone is interface only.** What it shows and what you type into it is
    visible to every mod in the game, and any code in the game can do whatever the phone
    can do (H2–H5); type nothing secret into it. Its clock shows the game's time zone, which
    is UTC unless `[sandbox] expose_timezone = true`.
15. **The phone's browser while it runs.** Whatever can drive the phone can act in a page
    where you are signed in, as you (H8); the launcher keeps the browser to the sites you
    listed and within their budgets, not to what you meant to do there. The sign-in window
    of `bastion-mc browser login` is an ordinary client of an X11 display (H13). Off by
    default.
16. **Versions within a family that were not started.** The companion assumes that every
    version of a family behaves like the representative that was run: their stand-ins are
    identical by construction, their behaviour was not observed (`COMPANION.md`).
17. **Bedrock: the game holds your Xbox identity.** In a Bedrock session the game's own
    sign-in library holds the account's Xbox identity — a refresh token of the Microsoft
    account, the key that signs its Xbox requests, Xbox and Minecraft tokens — for the whole
    session, and nothing can broker it. A game taken over (by a flaw that a hostile server,
    Realm, event server or add-on exploits, or through a compromised client) can use it, and
    can carry it away through any server, Realm or Xbox or Minecraft endpoint it is allowed
    to reach: the filtered network narrows those paths, it does not close them. A copy works
    until you sign out everywhere at Microsoft (which takes up to 24 hours). At stake: your
    Realms (with the owner's rights), your Minecoins, your Bedrock character and cape, your
    Xbox friends, and possibly your Java profile (not verified) (B15, B28).
18. **Bedrock: the licence check is answered by `mcpelauncher-client`**, and bastion-mc cannot
    tell a bought version from one that was not (B1).
19. **Bedrock: what the launcher cannot see.** The Bedrock side of the account — Minecoins,
    Realms, the character, Xbox friends — and `mcpelauncher-ui`'s Google sign-in, which stays
    on disk outside bastion-mc and `scram` (B38, B39).

## 6. Where the implementation deviates from the written requirements

| Requirement as written | What was built instead | Reason (observed on the target system) |
|---|---|---|
| `-XX:+DisableAttachAgent` | `-XX:+DisableAttachMechanism` (+ `-XX:-EnableDynamicAgentLoading` on 21+) | The named flag does not exist; HotSpot exits with "Unrecognized VM option". |
| seccomp filter *blocking* dangerous syscalls | allowlist (default `ENOSYS`) + kill-tripwire | `CONFIG_X86_X32_ABI=y` on Arch makes denylists bypassable; new syscalls stay denied. |
| SOCKS5/HTTP proxy or slirp4netns for egress | route-less netns + fake-IP DNS + transparent relay on launcher-held sockets | Minecraft's game connection (Netty) ignores Java proxy settings, so a proxy cannot both work and enforce. No extra binaries needed. |
| Token via "anonymous fd" / memfd | `AF_UNIX` socketpair on fd 0 | memfd and pipe were re-openable through `/proc/<pid>/fd` (§7 E3). |
| Refresh token "strictly in the kernel keyring" | yes (default), **plus** keyring isolation of the sandbox; optional `age` vault | An unhardened sandbox can read the keyring (§7 E2). |
| `--unshare-all --share-net` | explicit `--unshare-{user,ipc,pid,uts,cgroup}` + `--disable-userns`; net: private by default | `--unshare-all` only *tries* user/cgroup namespaces; `--disable-userns` needs explicit `--unshare-user`. |
| Hide `/sys` entirely | `/sys` contains only the GPU's own device directory and the few symlinks leading to it | Mesa cannot identify the driver without them (no hardware acceleration). |
| Instance dir read-only except four dirs | game root is a throw-away scratch dir; three dirs (`saves/ logs/ config/`) are the only instance paths mounted writable, `resourcepacks/` became read-only with an import command; `options.txt`/`servers.dat` are re-encoded by the launcher in both directions | A read-only root breaks settings, server list and server resource packs. A game-writable pack directory lets a pack install itself. Set `persist_files = []` for the literal behaviour. |
| "mlock … never swapped" | per-secret locked mapping (`memfd_secret`, or `mlock`); whole-process `mlockall` only when `RLIMIT_MEMLOCK` allows | Default limit is 8 MiB; `MCL_FUTURE` would make allocations fail. Transient TLS buffers are wiped on free instead. |
| Launcher "holds no credential while the game runs" | with the broker it holds the access token for the session (in secret memory, in a process that has confined itself) and the game holds none; with the phone's services also a Spotify access token and, in `totp` mode, the Realms TOTP secret — never a refresh token (the Spotify one stays in the token keeper) | The alternative is the token inside the JVM, readable by every mod. A Spotify access token is needed for every Web API request, the TOTP secret for every code the phone sends. |
| Landlock UDP rules for the launcher itself | sandbox only | The launcher's DNS responder answers to the game's ephemeral ports; a port rule cannot express "any port on this socket". The voice relay answers to the game's ephemeral ports in the same way, and sends to whatever UDP ports the rules name (J20). |
| CET/IBT, `-fstack-protector-strong`, `_FORTIFY_SOURCE=3` for the binary | applied to the C objects; Rust objects get PIE, full RELRO, BIND_NOW, NX, overflow checks | Stable rustc rejects `stack-protector`/`cf-protection`; a stable Rust binary cannot be CET-marked (`-z cet-report=error` fails to link). The PKGBUILD documents the nightly path. |
| ratatui TUI / iced GUI | a plain CLI in the process that holds the tokens; the iced window is a separate program that runs it with `--events` (§4.5) | Smallest attack surface in the process that handles tokens. |
| Each helper of the phone's services runs in a sandbox of its own (round 4's contract) | the Spotify token keeper runs in no sandbox, with the launcher's own process hardening (non-dumpable, no core dumps, every heap block wiped) | It stores each refresh token Spotify rotates in the kernel keyring or the age vault, which a sandbox would cut it off from and which the confined launcher can no longer reach. It holds the refresh token so that the launcher does not (H19). |
| A system-call allowlist, never a denylist (row 2 of this table) | the browser's sandbox has a denylist (`EPERM`), with `clone3` and every x32 number `ENOSYS` | Firefox installs its own system-call filter on its content processes and needs `seccomp` and `prctl` for that; an allowlist would have to follow every Firefox release. The x32 entry points, the reason for allowlists here, are closed all the same (H11). |
| Approvals decided and entered outside the game (§8, "Approval prompts in the game") | a Realms join is approved with a code shown outside the game and typed into the phone, inside it | When this was built, the front end's line to the launcher carried nothing but "stop", and a vanilla instance has no way to type at all; the code, not the place where it is typed, carries the decision — bound to its prompt in `code` mode, not in `totp` mode (J22). Since the fifth round the front end can write answers too (`answer realms <code>`): a Bedrock session, which has no phone, takes the code there or at the terminal, outside the game as written (B31); a Java launch still takes it from the phone only. |
| Research for the fifth round, §5.2 item 5: "a newly owned cape *will* trip the canary, and `canary accept` records it" | a gained cape is never a difference (as before that round); it is named at the next Java sign-in and pinned | Gaining a cape is not tampering, and an alarm at every event would train users to accept alarms. The note names the cape, so that its arrival is visible (B38). |

**Not built**, with the reason each is still open:

* **Login-protocol proxy.** With the broker, code in the JVM can still spend one join per
  game connection it opens, on a server of its choosing (J13). Removing that means the launcher performs the join itself,
  which requires terminating Minecraft's protocol encryption (the shared secret is
  encrypted to the server's key, so a relay cannot compute the server hash by watching):
  being the client towards the server and the server towards the game, per protocol
  version. Large and version-sensitive. It would also be the only place a packet-rate
  tripwire on game traffic could look at more than sizes and timing.
* **Signed server allowlist / out-of-band approval of new servers and mods.** A second
  factor kept on this machine is readable by the user it is meant to stop. The meaningful
  form is the mod-manifest model applied to the allowlist: signed with a key that is off
  the machine or in hardware.
* **Approval prompts in the game.** Built for one gate: Realms joins (J22), where the code
  is shown in the launcher's own output and typed into the phone — a departure from the
  design, which had the decision made *and entered* outside the game (§6). For the other
  gates nothing is built: enforcement would stay in the launcher — a mod runs in the same JVM
  as what it guards against —, whatever is shown in the game can be drawn over, and whatever
  is typed there can be typed by a mod, so the mod could only ever be where the player
  learns that the launcher is asking. The gates it would front (packs: built; servers,
  account requests: per-switch today) do not depend on it. The design is in
  `docs/notes/companion-mod.md`, part 2. A Bedrock session has no phone: there the code of a
  Realms or event-server join is shown and typed outside the game, as the design had it (B31).
* **Voice for servers that name a separate voice host.** Relaying datagrams to an address
  that no game connection vouches for — a second name resolution, a second destination —
  would be a different, weaker design than J20, to be decided on its own.
* **Hardware normalisation** (CPU count, `/proc/cpuinfo`, memory size): the GPU renderer
  string comes from the real driver and cannot be normalised by mounts, so the result
  would still be fingerprintable.
* **An immutable, verified `/usr` and JVM for the sandbox** (EROFS/composefs): needs a
  root-side component, against the unprivileged design.
* **A security-key dead man's switch**, **shadow stacks for the Rust code** (nightly-only
  flags; the kernel enforces user-space shadow stacks only when glibc opts the process in,
  and not IBT at all), **seccomp user notification** (must not decide on pointer
  arguments; Landlock already enforces paths and ports), **padding of sign-in traffic**
  (the observer sees the destination hosts anyway; rustls 0.23 has no record-padding setting),
  **cross-registry hash consensus** (an aid for the person who signs a profile, not
  enforcement: a bytecode capability diff exists — `profile lock`, `profile add` — and a
  registry cross-check exists for Modrinth alone — `profile check` —; agreement across
  registries is not checked, CurseForge's API needs a key).
* **Wayland compositors without the security-context protocol**: `auto` falls back to the
  session socket. Running gamescope there too (`--backend wayland`) is the candidate fix.
* **Keeping the Xbox identity out of the Bedrock game** (B15). On the Android route the
  game's sign-in library is inside the game and needs the refresh token there; nothing can
  broker it. Only the Windows (GDK) route would put token acquisition in code the launcher
  controls, and running that build takes decrypting the game outside Microsoft's protected
  path — circumvention, which is not built in any form.
* **LAN games, NetherNet and same-machine servers for Bedrock** (B35): LAN and loopback
  servers need a per-server `allow_private` in the shared server type (a product decision);
  NetherNet (WebRTC: friends' worlds and NetherNet Realms) connects to addresses negotiated
  inside its signalling, which the relay cannot tie to a name or an approval
  (`docs/notes/bedrock-research.md` §4.2).
